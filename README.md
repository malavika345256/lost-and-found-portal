# College Lost and Found Portal

The existing static pages are served by Express from the project root. API data is stored in MongoDB database `lost_found_portal`. Authentication uses a JWT in an HttpOnly cookie (the APIs also accept `Authorization: Bearer <token>` for clients that prefer bearer tokens).

## Run locally

1. Install Node.js 20 or newer and install MongoDB Community Server, or create a MongoDB Atlas cluster.
2. In this folder, install packages and create local configuration:

   ```powershell
   npm install
   Copy-Item .env.example .env
   ```

3. Edit `.env`. Keep the local URI as shown for MongoDB Community Server, or replace `MONGODB_URI` with your Atlas connection string. Replace `JWT_SECRET` with a random secret of at least 32 characters; set the admin password to a strong value of at least 16 characters.
4. For MongoDB Compass, connect to `mongodb://127.0.0.1:27017`. The database and collections are created automatically when records are written. Start the MongoDB service before starting the app.
5. Create or reset the administrator account:

   ```powershell
   npm run seed:admin
   ```

   This uses `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` from `.env`. It updates only an existing administrator at that email, refuses to promote a student account, and refuses to create a second administrator under a different email. Registration through the public API can only create regular users.

   If the admin email or password was forgotten, run `npm run recover:admin`. It resets the single existing administrator, or creates one if the database has none; it refuses ambiguous multiple-admin or student-email cases. The generated password is stored only in the gitignored `.env` as `ADMIN_PASSWORD`, and the login ID is saved as `ADMIN_EMAIL`. Sign in at `/admin.html`.
6. Start the portal:

   ```powershell
   npm run dev
   ```

   Open `http://localhost:3000`; the root URL redirects to the student login page. After student login, the authenticated homepage is `index.html`. Use `npm start` for a non-watch server. Check `http://localhost:3000/api/health` for the MongoDB connection status.

For Atlas, create a database user, allow the development machine's IP in Network Access, copy the driver's connection URI into `MONGODB_URI`, and URL-encode special characters in the database user's password. Do not commit `.env`.

## Deploy to Render with MongoDB Atlas

This project serves its frontend, API, and Socket.IO from one Express service. The checked-in `render.yaml` configures a Render Node web service with `npm install`, `npm start`, and `/api/health` as its health check. API URLs are relative, so they work on the deployed origin without frontend URL changes or CORS configuration. `package-lock.json` currently omits the declared `socket.io` dependency, so regenerate it on a networked development machine (`npm install`) and commit the updated lockfile to restore reproducible `npm ci` installs.

1. Create a MongoDB Atlas cluster and a database user with a strong password. In Atlas Network Access, allow connections from Render. For a hobby setup without static outbound IPs, Atlas may require `0.0.0.0/0`; use a narrower allowlist when your Render plan provides fixed outbound IPs. Use the Atlas driver URI and URL-encode reserved characters in the database user's password.
2. In Render, choose **New > Blueprint**, connect the GitHub account that has this repository, and select the repository and branch. Render reads `render.yaml` and creates the web service. If Render cannot use the Blueprint, create a **Web Service**, set the root to the repository root, build command to `npm ci`, and start command to `npm start`.
3. In the Render service's Environment settings, set `MONGODB_URI` to the Atlas URI. `JWT_SECRET` is generated by the Blueprint; otherwise create a random secret of at least 32 characters. Keep `NODE_ENV=production` and `COOKIE_SECURE=true`. The service does not need `FRONTEND_ORIGIN` because frontend and API share an origin.
4. Deploy and wait for the service to become healthy. Open `/api/health`; it should return `{"status":"ok","database":"connected"}`. A disconnected database or failed deployment should be diagnosed from the Render service logs and the Atlas Network Access/database user settings.
5. Create the administrator once the service is deployed. Temporarily add `ADMIN_NAME`, `ADMIN_EMAIL`, and a strong `ADMIN_PASSWORD` under Render Environment, then run `npm run seed:admin` in the Render Shell. Remove `ADMIN_PASSWORD` from the service environment after successful seeding. The seeding script will not promote a student account or create a second administrator. Sign in at `/admin.html`.

After connecting the repository, Render deploys new commits to the selected branch automatically. To check logs, open the service in Render and choose **Logs**; use **Manual Deploy** to redeploy the latest commit on demand. Test the public site on a laptop and phone by opening the service URL, registering/logging in, and checking report listing/search and the relevant account/admin flows. Confirm responsive layouts, image upload, and notification/chat behavior on both devices.

The local project folder provided for inspection does not currently contain Git metadata, and this environment could not fetch the supplied GitHub URL. Confirm before creating the Render service that the connected GitHub repository contains these deployment changes (`server.js`, `.gitignore`, `render.yaml`, and `README.md`).

The default setup serves pages and API from the same origin. If you host the frontend separately, set `FRONTEND_ORIGIN` to its exact origin. For a cross-site HTTPS deployment, set `COOKIE_SECURE=true` and `COOKIE_SAME_SITE=none`; same-site deployments can keep `COOKIE_SAME_SITE=lax`.

## Postman

Import [the Postman collection](postman/Lost%20and%20Found%20Portal.postman_collection.json), then set the `baseUrl` variable to `http://localhost:3000`. Enter values for `userEmail`, `userPassword`, `adminEmail`, and `adminPassword`. Student registration requires an `@ced.alliance.edu.in` email address, as the existing form requires.

Run the `Health` request first. Register both example students, log in as the first student, and create a lost report. Log in as the second student and create a similar found report; then submit claims from two different student sessions for the same found item. Each claim is stored separately as pending (shown as “Pending Verification”), and each student sees only their own claim in My Reports. Log in as the administrator to review claimant details and decide each claim. Approval atomically reserves the found item, marks it returned, approves one claim, rejects the remaining pending claims with a reason, and creates in-portal notifications for affected claimants. Rejection reasons and admin identity/timestamps are recorded. A match notification alone never approves a claim. The `Login user` request establishes the `portalToken` cookie in Postman's cookie jar for `localhost`; keep requests on the same host. Postman cookie handling automatically sends the HttpOnly cookie back. Logging in as another account replaces the cookie, so log in again as the required student or admin before each role protected request.

The collection includes lost and found report creation, filtering, report updates and deletion, claims, competing claims, proof requests and submissions, claim decisions, conversations, messages, notifications, history, contact, and administrator operations. Contact requests first log in as the student because the contact page and API are protected. For unauthenticated page checks, clear Postman cookies for localhost before requesting `/index.html` or another student page; authenticated cookie requests should return the page, and logout should make those requests redirect to login. It also includes checks for missing registration fields, duplicate registration (409), invalid credentials (401), malformed IDs (400), and missing authentication (401). The claim answers and proof are private and the item public endpoints omit them.

Student credentials use only `@ced.alliance.edu.in`, the domain present in the existing registration code and backend. Student login is `POST /api/auth/login`; administrator login is separate at `POST /api/admin/auth/login`. The admin request requires an account with the `admin` role set by the seed script. A student cookie receives 403 from administrator endpoints.

The Lost & Found Assistant folder tests `POST /api/chatbot/message` with an authenticated student session. It uses predefined guidance and searches current public reports in MongoDB; it does not call an external AI provider. Empty messages return 400 and messages over 1000 characters return 413.

The server redirects unauthenticated requests for the student homepage, dashboard, item reporting, search, history, and contact pages to `/login.html`. Student pages and item/contact APIs require a student session. `/admin.html` shows the existing administrator sign-in form until a valid administrator session is present; student sessions are redirected to the student homepage. Authenticated HTML pages are sent with no-store cache headers. Logout clears the HttpOnly cookie and redirects to the student login page.

Example successful responses:

```json
{ "message": "Registration successful.", "user": { "id": "...", "name": "Student", "email": "student@ced.alliance.edu.in", "role": "user" } }
```

```json
{ "message": "Report submitted.", "item": { "_id": "...", "type": "found", "itemName": "Wallet", "status": "pending", "reporter": "..." } }
```

```json
{ "message": "Claim submitted for administrator verification.", "claim": { "id": "...", "item": "...", "status": "pending", "createdAt": "..." } }
```

## API reference

All request bodies are JSON. Successful examples use the following shape; error responses use `{ "message": "..." }`.

| Method and path | Purpose | Expected success |
| --- | --- | --- |
| `POST /api/auth/register` | `{ "name":"Student", "email":"student@ced.alliance.edu.in", "password":"ExamplePass123!" }` | 201; duplicate 409, invalid fields 400 |
| `POST /api/auth/login` | Student login, e.g. `{ "email":"student@ced.alliance.edu.in", "password":"ExamplePass123!" }` | 200 and HttpOnly cookie; wrong credentials 401; invalid or personal email 400 |
| `POST /api/admin/auth/login` | Administrator-only login using the seeded admin account | 200 and HttpOnly cookie; non-admin account or bad password 401 |
| `POST /api/auth/logout` | Clear cookie | 200 |
| `GET /api/auth/me` | Current account | 200; unauthenticated 401 |
| `GET /api/items?q=wallet&category=Wallet%20and%20Purse&type=found&location=Library&dateFrom=2026-01-01&dateTo=2026-12-31` | Student-only item search | 200; response excludes private verification/contact and handover data; ID card records are redacted |
| `GET /api/map/lost-items?dateFrom=2026-01-01&dateTo=2026-12-31&category=Books%20and%20Notebooks&status=pending` | Student-only lost report map summary grouped by stored location and category, including safe report IDs for links to `item.html?id=...` | 200; counts only `type: "lost"`, separates active and resolved totals, omits private contact, handover, verification, and claim data; invalid dates, categories, or statuses return 400 |
| `GET /api/items/:id` | Student-only item details | 200; bad ID 400, missing 404; ID card details are redacted |
| `POST /api/items` | Authenticated report, e.g. `{ "type":"lost", "itemName":"Wallet", "description":"Brown leather wallet", "category":"Wallet and Purse", "location":"Library", "date":"2026-10-23" }` | 201; `type` is `lost` or `found`; opposite-type possible matches create persistent notifications |
| `POST /api/reports/lost` and `/api/reports/found` | Page-specific authenticated report submissions | 201; the route sets `type` regardless of a client-supplied type value |
| `PATCH /api/items/:id` | Owner edits own report fields; admin can also set moderation status | 200; unauthorized owner 403; report type/review status are distinct from recovery status |
| `DELETE /api/items/:id` | Owner/admin deletes report | 200; unauthorized owner 403 |
| `POST /api/claims` | `{ "itemId":"...", "reason":"A private explanation of how I can identify this item", "proof":"Optional proof description" }` (`details` remains supported) | 201; separate students can claim the same item; duplicate claim by one student returns 409; own-item claims are rejected |
| `GET /api/claims/my` | Current user's claims, including own decision status/reason and found-item details | 200; other students' claims and private answers are not returned |
| `PATCH /api/claims/:id/proof` | Claim owner submits requested proof, e.g. `{ "proof":"Photo confirms identifying mark" }` | 200; only own pending claim |
| `GET /api/claims/item/:itemId` | Admin-only private claim comparison | 200 |
| `PATCH /api/claims/:id/status` | Admin decision `{ "status":"approved", "reason":"Ownership details verified" }` or `{ "status":"rejected", "reason":"Details did not match the item" }` | 200; decisions include admin and timestamp; rejected claims require no client reason for backwards compatibility; approval race loser returns 409; non-admin 403 |
| `PATCH /api/claims/:id/request-proof` | Admin request `{ "request":"Please provide a photo showing the identifying mark." }` | 200; pending claims only |
| `POST /api/conversations` | `{ "itemId":"..." }`; creates or returns item conversation | 201 |
| `GET /api/conversations` | Participant's conversations | 200 |
| `GET /api/conversations/:id/messages` | Read messages and mark them read | 200 |
| `POST /api/conversations/:id/messages` | `{ "body":"I can meet at the student affairs office." }` | 201 |
| `GET /api/dashboard` | Current user's reports, claims, chats, and notifications | 200 |
| `GET /api/matches` | Possible-match pairs involving one of the current student's reports, including public lost/found details and match status | 200; student-only, and each student sees only pairs involving their own report |
| `GET /api/notifications` | Current user's notifications | 200 |
| `PATCH /api/notifications/:id/read` | Mark own notification read | 200 |
| `POST /api/chatbot/message` | `{ "message":"How do I report a lost item?" }` | 200 with predefined guidance, safe report search results, and portal links; 400 empty, 413 over 1000 characters |
| `GET /api/admin/dashboard` | Aggregate counts | 200; non-admin 403 |
| `GET /api/admin/users` | User list | 200; admin only |
| `PATCH /api/admin/users/:id/role` | `{ "role":"user" }` or `admin` | 200; admin only |
| `GET /api/admin/claims` | Claim review list with found-item details, claimant count, private answers, status, and decision audit fields | 200; admin only |
| `GET /api/admin/reports` | All reports with reporter | 200; admin only |
| `GET /api/admin/contact-messages` | Submitted contact messages | 200; admin only |
| `POST /api/contact` | `{ "name":"Student", "email":"student@example.edu", "subject":"Question", "message":"..." }` | 201; student authentication required |

## Collections and privacy

Mongoose uses `users`, `items`, `claims`, `conversations`, `messages`, `notifications`, `potentialmatches`, and `contactmessages` in the configured database. Passwords use bcrypt hashes. Item `type` is `lost` or `found`; `status` is the report review state; `recoveryStatus` is `open`, `claim_pending`, or `returned`. Claims are separate documents with an authenticated claimant, submission timestamp, status, and admin decision audit. The item's atomic claimant set prevents duplicate claims by one student, and an atomic approved-claim reservation serializes approval attempts without rewriting existing claim records. Matching compares name, category, description, location, and report date, and requires item-detail similarity rather than category alone. `potentialmatches` stores both linked report IDs with a unique pair key; matching notifications are deduplicated per student and report pair. Students can read and mark only their own notifications. The assistant is a separate responsive interface and authenticated endpoint; its history stays in the open chat window for that page session. It uses predefined responses and authorized public report search, with no paid API key. Item-to-item chat remains separate. Image inputs accept JPG/JPEG/PNG/WEBP images up to 5 MB as base64 data URLs.

The campus map endpoint groups only lost reports by their stored location text and category. Location grouping ignores letter case and surrounding/repeated spaces (`Library` and `library` combine), while distinct names such as `Library Block` stay separate. The Leaflet view uses the mapped Alliance University campus feature as a campus-level center; report locations without verified building coordinates appear in ranked count bars and are not given fabricated map pins. Leaflet tiles are served by OpenStreetMap with visible attribution.

Student navigation contains Home, Report Lost, Report Found, Matches Found, Campus Map, and Contact in that order. Matches Found is backed by saved potential-match pairs and shows the public details for both reports to their reporters. The unread notification badge and saved recent notifications are available from Matches Found. The existing item-to-item conversation panel and the separate Lost & Found Assistant remain available.

### Existing database records

No collection is cleared and no report type is inferred from status. Records that already have `type: "lost"` or `type: "found"` continue to display that type. Older records missing `type` or recovery status display as **Unclassified** until an administrator checks the original report and manually corrects that specific document. Do not bulk-set missing types to `lost` or infer them from `status`; report status does not reliably encode item type. New reports explicitly store both type and `recoveryStatus`. Startup creates the unique notification deduplication index without rewriting report documents.

At inspection, the configured database contained two reports with `type: "lost"` and none with `type: "found"`; neither was missing its type field. That means a found report may have been stored with the wrong value, but the stored documents do not say which one. Verify the report against its original submission before changing it. For a confirmed report, an administrator can correct only that document in Compass or with `db.items.updateOne({ _id: ObjectId("VERIFIED_REPORT_ID") }, { $set: { type: "found" } })`. No automatic data migration is safe without that review.

To inspect legacy reports safely in MongoDB Compass, filter the `items` collection with `{ "type": { "$exists": false } }` and review each report against its original submission before editing. The administrator report table has a type correction control that saves only after an administrator chooses Lost or Found. Inspect historical `status: "resolved"` reports separately before deciding whether a recovery status can be recorded.

During read-only inspection on 2026-10-24, the configured database contained two pending College ID Card reports, dated 2026-10-22 and 2026-10-23, both stored as `type: "lost"`. Their stored names, category, and location do not show which report was originally found. The app leaves those records unchanged until an administrator verifies and corrects the right record from the original submission evidence.
